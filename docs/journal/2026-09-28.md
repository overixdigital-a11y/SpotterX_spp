# 2026-09-28

## Contexto

El usuario reporto que en el panel del gym los datos de los clientes no figuraban:

- **Accesos** (`/gimnasio/accesos`): la lista de "Accesos recientes" mostrava la palabra literal **"Usuario"** con la fecha/hora de entrada o salida, sin el nombre real.
- **Miembros** (`/gimnasio/miembros`): la tabla "Miembros Registrados" mostraba **`@sin_username`** en todos los usuarios y la columna de nombre/apellido vacia.

Contexto relevante: venia de cerrar la migracion `00047` (hardening de permisos EXECUTE, commit `136038c`), asi que la primera hipotesis fue una regresion de esa migracion. **No lo fue.**

## Decisiones

- **Alcance acotado a 3 paginas** por decision del usuario: `accesos`, `miembros` y `cobros`. El **kiosk `pantalla/page.tsx` se deja afuera** a proposito, aunque tenga el mismo bug (anotado como pendiente).
- **Helper compartido en vez de corregir cada pagina**: la leccion del embed ya existia en AGENTS.md pero se aplico pagina por pagina, y por eso reaparecio roto en 5 lugares. Se consolida en `src/lib/profiles.ts`.
- **Fallback canonico `full_name` → `email` → `username` → `"Sin nombre"`**: antes priorizaba `username` sobre `email`. El email identifica a la persona; el username es decorativo. Ademas se **elimino el string inventado `@sin_username`**, que se mostraba al usuario como si fuera un valor real.
- **No se investiga la causa raiz del embed**: el fix lo **rodea** (consulta separada, que sí anda) en lugar de repararlo. Se deja documentado explicitamente para no vender humo.

**Falsas hipotesis que se descartaron con evidencia (importante para no repetirlas):**
1. **No era regresion de la `00047`**: esa migracion solo cambia permisos `EXECUTE` de funciones; no toca `gym_memberships`, `gym_access_logs`, `profiles` ni sus policies.
2. **No era RLS**: `gym_memberships`/`gym_access_logs` dejan pasar al owner via `exists (select 1 from gyms g where g.id = gym_id and g.owner_id = auth.uid())`, y `profiles` tiene `select using (true)` sin policies que se auto-referencien => **no hay recursion**.
3. **No faltaban los datos**: se corrio `select email, username, full_name from public.profiles` y **los 11 perfiles tienen `full_name` completo**. El sintoma (todos los campos ausentes en la fila) lo produce `r.profiles === null` del embed roto, no un `null` en la base. Esto casi hizo perder tiempo: cuando los 3 campos llegan a la vez como ausentes, el embed es el sospechoso, no los datos.
4. **La primera lectura del reporte llevo al error**: ver `@sin_username` se interpreto como "`username` llego pero `full_name` no", cuando en realidad `sin_username` es un **string hardcodeado en el frontend** que se imprime cuando `username` tambien es null. La clave de diagnostico es que `accesos` cae a `"Usuario"` y `miembros` a `"sin_username"`: **mismo `profiles === null`, dos fallbacks distintos**.

Verificacion: `npm run lint` 0 errores (7 warnings preexistentes de `<img>`) y `npm run build` OK (47 rutas).

**Cierre del kiosco (mismo dia, commit posterior):** el usuario confirmo que `accesos`, `miembros` y `cobros` quedaron bien, y que **`pantalla/page.tsx` seguia roto**. Era el sexto y ultimo embed del panel del gym.
- El **handler realtime ya consultaba `profiles` por separado** (L154, `.eq("id", row.user_id).maybeSingle()`) => los check-ins en vivo siempre mostraron el nombre bien. Solo fallaba el **load inicial**, que usaba el embed. Por eso no hubo que tocar la parte de realtime.
- `ProfileLite` ahora incluye `avatar_url` (columna de `00001_init.sql:22`) porque el kiosk lo necesita para los avatares; el select del helper lo trae siempre.
- Ojo con el tipo: `Person` usa `user_id` pero el `Map` de `fetchProfiles` esta indexado por `id` => hay que armar `{ user_id, ...profile }` con un `personOf(userId)`, no pasar el profile crudo.

## Piloto de imagenes REVERTIDO en produccion (29/09/2026) - POSTMORTEM

**Resultado:** no sirvio. El usuario lo probo en el celular y reporto "no se ven las imagenes" mas "modificaste la conformacion de la rutina y no puedo agregar reps/series". Revertido con `git revert` (commits `bf9b24c` + `75801ba`); `src/`, `scripts/`, `package.json` y `next.config.ts` quedaron **identicos a `a9ff946`** (verificado con `git diff a9ff946..HEAD --stat -- src/ scripts/`, vacio).

### Bug 1: NINGUNA imagen se mostraba (0/25). Error mio.

`exerciseImage(name)` hacia `IMAGES[name.toLowerCase().trim()]` pero el generador escribia las claves **tal cual**, con mayusculas y acentes (`"Press de banca"`, `"Sentadilla búlgara"`). En JavaScript el acceso a una propiedad de objeto **SI distingue mayusculas**, asi que se buscaba `"press de banca"` contra un mapa cuya clave era `"Press de banca"`: **0 de 25 coincidencias, siempre**. Verificado:
```
claves: 25 | claves en minusculas: 0
MATCH con el codigo actual: 0 / 25   <-- ninguna imagen, nunca
MATCH si fueran minusculas: 25 / 25
```
Las URLs no tenian nada que ver: respondian **HTTP 200 / image/jpeg / ~70 KB**. El problema era el emparejamiento, no el hosting.

**Por que NO lo detecto NADA (la parte importante):** pasaron las 4 verificaciones y aun asi no se vio ni una imagen.
- `npm run lint`: el tipo `Record<string,string>` es valido con cualquier casing. No hay forma de que el linter lo detects.
- `npm run build`: compila igual. Rutas identicas (51 = 51).
- **Verificacion de URLs (25/25 HTTP 200):** verificaba que las URLs existieran, NO que el lookup encontrara la clave. Dio verde con el feature 100% muerto.
- `--check` del generador: validaba que cada nombre español existiera en los seeds `00018`/`00019`. Estaba perfecto. Nunca valido el **consumo** del mapa.

**LECCION (la que hay que conservar):** cuando un mapa generado lo consume un lookup que normaliza, el generador tiene que emitir las claves **en la misma normalizacion que el consumidor**, y el `--check` tiene que ejercitar el lookup real, no la existencia de los datos. Concretamente: `const hit = keys.filter(k => IMAGES[k.toLowerCase().trim()]).length; if (hit !== keys.length) throw ...`. Regla general: **"el generador verifica que el dato existe" no es lo mismo que "el consumidor lo encuentra"; hay que probar el consumidor.** Un dato generado que nunca se leyo de verdad es indistinguible de un dato que funciona.

Bug propio relacionado, del mismo tipo: en la revision de la UI ya se habia visto el mapeo erroneo de `Flexión de pino` (el dataset no tiene "Pike Push-Up", se le habia puesto la foto de un Handstand Push-Up). Se detecto leyendo el mapa contra el dataset, no con ningun test. Dos bugs de mapeo en la misma sesion = el mapa curado a mano es el punto mas frágil del feature.

### Bug 2 (preexistente, NO lo causo este feature): no se pueden cargar series sin disciplina

`alumno/[id]/page.tsx` L1509: el editor de series (`+ Serie`, Reps, Peso, Desc) solo se renderiza si `isSeriesDiscipline(routineForm.discipline)`, y `SERIES_DISCIPLINES` = `musculacion | crossfit | calistenia | funcional`. Pero `routineForm.discipline` arranca en `""` (L551) e `isSeriesDiscipline("")` devuelve **false** (porque `""` es falsy).

**Consecuencia:** creas una rutina y no tocas un chip de disciplina => nunca aparece el editor de series, solo los campos planos. "Otras" (L1415) tampoco da series. Es la causa mas probable de lo que el usuario reporto, y **sigue vigente despues del revert**. Verificado que el feature no lo toco: `git diff a9ff946..HEAD` no toca `addSeries` / `removeSeries` / `updateSeriesField` / `toggleSeries`.

Ademas: como el bug 1 hacia que los 6 `<ExerciseThumb>` devolvieran `null`, **el revert no cambia ni un pixel de lo que el usuario vio**. Por eso no se puede atribuir el problema de conformacion a este feature.

### Decision
**No se reintenta el piloto ahora.** El enfoque (mapa TS sin tocar la base, degradacion con `null`) era correcto y seguro, pero la ejecucion fallo en lo basico, y 25 imagenes sobre 156 no cubrian ni los ejercicios tipicos del usuario. Si se retoma: (a) emitir claves en minusculas desde el generador + test del lookup, (b) empezar por cobertura real de las 4 disciplinas de fuerza, (c) revisar el mapeo a mano contra el dataset antes de deployar.
