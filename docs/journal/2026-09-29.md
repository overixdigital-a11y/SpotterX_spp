### Lecciones

- **42601 en un `end if;` casi siempre es una linea perdida al copiar**, no un error de

## Lote 42b - Fix: `userId` null en toda la consola admin (commit `aa9b103`)

### Sintoma
El usuario intento subir una foto en `/admin/catalogo` y salio
`No se pudo identificar tu usuario`. Mismo toast en el boton de video.

### Hipotesis descartada
Primero sospeche una **carrera** entre dos cargas: la tabla se dibuja cuando
termina la query del catalogo (1 request en paralelo) mientras el
`AuthProvider` todavia esta resolviendo `getUser()` + `profiles` (2 requests en
cadena), asi que el `+` quedaba pulsable con `userId === null`. La carrera
existe y por eso se agrego el gate de `authLoading`, pero **no era la causa**.

### Causa raiz real
`useAuthState()` lee un contexto de React. **Sin `AuthProvider` en el arbol no
lanza error: devuelve el default del `createContext`**
(`auth-context.tsx:14-19`), que trae `userId: null` de forma **permanente**.

El `AuthProvider` estaba montado en:

| Montado | |
|---|---|
| `SocialShell` | si |
| `TrainingShell` | si |
| `GymShell` | si |
| `MarketShell` | si |
| `(checkin)/layout.tsx` | si |
| **`(admin)/layout.tsx`** | **NO** |

`AdminShell` es el unico shell sin provider, y tampoco estaba en el layout root.
O sea: en `/admin/catalogo`, `userId` era **siempre** `null` y los guards
`if (!userId)` de las lineas 363 y 420 disparaban siempre. No podia funcionar,
ni en el escritorio ni en el celu.

### Por que paso 2 lotes inadvertido
El Lote 42 arranco leyendo "**0 ejercicios con `image_url`**" y lo registro como
"el bucket esta vacio => se puede reestructurar el modelo sin riesgo". La otra
lectura era: "**la subida de fotos del Lote 41 nunca funciono**". Una feature
que nunca se ejercita no se valida con un conteo de filas; hay que probarla con
un **write real** (subir una foto) antes de darla por buena.

Ademas el bug era **silencioso** en la creacion de catalogo: `created_by`
quedaba `null` sin ningun error visible.

### Cambios
- `src/app/(admin)/layout.tsx`: monta `<AuthProvider>` envolviendo `<AdminShell>`.
  Se eligio el layout y no el shell porque el layout es el limite del route group
  (envuelve `children`) y no obliga a reindentar las 150 lineas de `AdminShell`.
- `src/app/(admin)/admin/catalogo/page.tsx`: `const { userId, loading: authLoading }`
  y gate `{loading || authLoading ? <spinner> : ...}`.

### Lecciones
1. **Un contexto de React sin provider degrada en silencio**, a diferencia de
   casi todo lo demas, que revienta. Si un `useContext` devuelve siempre
   `null`/`false`, suspectar primero que **falta el provider**, no que la data no
   llego. Para auditarlo: buscar `<AuthProvider` en `src` y comparar contra los
   shells que usan `useAuthState()`.
2. **Una feature de escritura no se valida con un conteo de filas.** "0 filas con
   `image_url`" es ambiguo entre "nadie subio nada todavia" y "nadie puede
   subir". La diferencia se prueba con un write, no con un select.
3. **Regla**: todo shell o route group que consuma `useAuthState()` tiene que
   montar `AuthProvider`.

### Pendiente de barrido (no hecho a proposito)
46 archivos hacen `const { userId } = useAuthState()` sin mirar `loading`. Los que
solo comparan ids son inofensivos con `null`; los que hacen `if (!userId) { error }`
y abortan la operacion siguen expuestos a la carrera auth-vs-query. Candidato a
barrido en un lote propio.

# Lote 42c - Fix: el material propio no se actualizaba entre pestanas (commit `edc5453`)

## Contexto

El usuario subio una foto a **Ab wheel** desde `/admin/catalogo` y, al crear
una rutina con el profesor, las miniaturas seguian mostrando
`/exercises/Ab_Roller.webp`. Al principio dijo "ya se arreglo", pero en ese
momento no habia ningun commit: lo que habia hecho era **recargar la pagina**.

## Diagnostico (por que los datos estaban bien y igual se veia la vieja)

Primero se verifico la base por REST, y **todo estaba correcto**:

```
[{"name":"Ab wheel",
  "image_urls":["https://.../media/31144c40-.../ejercicios/673d4efc-...jpg"],
  "demo_url":null}]
```

- `image_urls` es un **array** de 1 elemento (confirmado con `-is [array]`; el
  `ConvertTo-Json` de PowerShell desenvuelve arrays de 1 elemento y lo hacia
  parecer un string).
- La URL publica responde **HTTP 200, 804278 bytes**.
- `ExerciseThumb` ya priorizaba la foto propia sobre la estatica
  (`propia = fotos[0]`, `statica = propia ? null : exerciseImage(name)`).

O sea: la base, Storage, la RPC y la logica de prioridad estaban bien. Lo unico
malo era **el estado en el navegador**.

La causa era `src/lib/exercise-media-map.ts`, que era esto:

```ts
if (cache) return cache;   // sin vencimiento
```

Una cache a nivel de **modulo**, que se llena una vez y queda para siempre. La
memoria de un modulo JS es **por pestana**, asi que:

| pestana | que paso |
|---|---|
| admin | subio la foto, `invalidate()` vacio **su** copia => al navegar ve la foto nueva |
| rutina (u otro dispositivo) | ya tenia el mapa cacheado **vacio** de antes, y no volvia a preguntar => servia el snapshot viejo para siempre |

El usuario lo confirmo de forma indirecta: "el administrador lo ingreso en otra
ventana". Ese es exactamente el escenario que rompe, y era el caso mas comun:
subir material en una pestana y mirar rutinas en otra.

Ademas `resetExerciseMediaMap()` era el unico invalidante y lo llamaba **solo**
la pagina del admin.

**Por que relajo a los ojos**: recargar la pagina borra la memoria de la pestana,
el mapa se vuelve a pedir a la base, y ahi encuentra la foto. Por eso "parecia"
que se arreglaba solo. Con 64 fotos y 64 videos por cargar, eso iba a ser
perder tiempo creyendo que se habia subido mal algo.

## Decisiones

1. **Store con `useSyncExternalStore`, no pasar un `version` por props.** El
   repo tiene 3 pantallas que consumen el mapa y cada una tendria que acordarse
   de re-renderizar. Con `useSyncExternalStore` en `ExerciseThumb` (el unico
   lugar que dibuja) las miniaturas se repintan solas y **no se toco ninguna de
   las 3 pantallas**.
2. **Realtime como mecanismo principal, TTL como red.** Un TTL solo NO arregla

## Lecciones

1. **Una cache sin vencimiento, a nivel de modulo, es un bug por pestana, no un
   bug de rendimiento.** El sintoma (dato viejo) se confunde con "no se guardo"
   o "no llego", y por eso se le echa la culpa a la base. **Antes de tocar la base,
   verificar el estado del cliente**: si recargar lo arregla, el dato estaba
   bien y lo que estaba viejo es el snapshot.
2. **Verificar el tipo antes de culpar al schema.** `ConvertTo-Json` de
   PowerShell desenvuelve un array de 1 elemento y devuelve `"https://..."` con
   comillas, que parece un string. Con `-is [array]` seaclara en una linea.
   Si el `image_urls` hubiera sido un string de verdad, el `.filter()` del
   `catch` habria tirado `TypeError` y el mapa habria quedado vacio para todos
   los ejercicios.
3. **"Ya se arreglo" sin commit hay que verificarlo.** El codigo estaba
   intacto (`git log`, working tree limpio, la linea 49 seguia sin TTL) y lo
   que se habia arreglado era una recarga. Con la base verificada y el
   worktree limpio, la unica variable que queda es el estado del cliente.
4. **Un TTL no arregla "la pestana ya abierta".** Sirve para "navegue despues
   de subir", no para "subieron mientras yo miraba". Para el segundo caso hace
   falta un aviso: realtime. Son dos problemas distintos y el TTL solo cubre
   uno.
5. **Infraestructura puesta y sin usar** (`exercises` en `supabase_realtime`
   desde la 00018, sin ningun `.on("postgres_changes")` en el repo). Antes de
   escribir una migracion para "habilitar realtime", grepear si la tabla ya
   esta en la publicacion.
